Section 1

New Hospital Setup

Complete deployment guide for installing Puru at a fresh hospital site — from hardware verification through full service handover.

⏱ Total estimated time: ~55 – 70 minutes
☑

Pre-Arrival Checklist ~15 min

Verify everything before you leave the office

Complete these checks before departing. Nothing is worse than arriving on-site and realizing the hospital record hasn't been created or credentials aren't generated yet.

  • Confirm hospital record exists in Puru Control Center → Management → Hospital tab
  • Confirm credentials are generated — Management → Credentials tab, status must show active
  • Download or send the setup package — either download directly or send to hospital inbox via the Control Center
  • Pack your gear: laptop with puru-nucleus installer, USB drive with offline installer (backup), hospital's network details (IP range, gateway)

Hardware & Network Verification ~10 min

Verify server specs, Docker installation, and connectivity

Ensure the hospital's server meets minimum requirements and has the necessary software installed before proceeding. If anything is missing, stop and resolve it first.

  • Verify server hardware — minimum 8 GB RAM, 4-core CPU, 100 GB+ disk
  • Verify Docker is installed (minimum 20.x) 
docker --version
  • Verify Docker Compose 
docker compose version        # v2 (preferred)
docker-compose --version      # v1 (legacy)
  • Verify MySQL client is installed 
mysql --version
  • Verify internet connectivity to the container registry 
curl -s https://cloud.google.com -o /dev/null -w "%{http_code}"
  • Note the server's local IP address (you'll need it in Step 4) 
# Linux
hostname -I | awk '{print $1}'

# macOS
ipconfig getifaddr en0
⚠ If Docker is not installed, install it first. Do NOT proceed without Docker. Refer to the official Docker install docs for the server's OS.
2

Install puru-nucleus ~5 min

Copy the binary and verify it runs

Transfer the puru-nucleus binary to the hospital server. Use USB if internet is unreliable. The install location differs by platform.

  • Copy puru-nucleus binary to the server (via USB or download)

Linux

sudo cp puru-nucleus /usr/local/bin/puru-nucleus
sudo chmod +x /usr/local/bin/puru-nucleus

Windows

copy puru-nucleus.exe C:\PuruNucleus\puru-nucleus.exe

macOS

sudo cp puru-nucleus /usr/local/bin/puru-nucleus
sudo chmod +x /usr/local/bin/puru-nucleus
  • Verify the installation 
puru-nucleus --version
3

Activate License ~3 min

Import credentials and link hospital to cloud

This step connects the hospital to the Puru cloud. The credentials file and hospital email are required. puru-nucleus will query the cloud to retrieve the hospital code, name, and license.

  • Open puru-nucleus GUI in browser at http://localhost:9090 
# Or use CLI mode:
puru-nucleus setup
  • On the Activation screen, click "Browse File" or "Paste JSON" to import the credentials file from the setup package
  • Enter the hospital's registered admin email address
  • Click "Activate" — wait for confirmation
ℹ On success, puru-nucleus saves configuration and license files to the local config directory.
💡 If activation fails with "Hospital not found", verify the email matches exactly what was entered in the Puru Control Center Hospital tab. Check for trailing spaces or capitalization differences.

4

Configure Infrastructure ~5 min

Set MySQL, Docker Compose path, and server IP

Enter the local infrastructure details. These values are saved to the nucleus config and used by the automated setup wizard in the next step.

  • Enter MySQL connection: host, port, root user, root password
  • Set Docker Compose file path (use the wizard default or customize)
  • Set the server's LAN IP address (the one you noted in Step 1)
  • Click "Save & Continue"
💡 Ask the hospital IT admin for the MySQL root password. If MySQL is not yet installed, the wizard will containerize it in the next step.
5

Run Automated Setup ~15–20 min

9 automated steps — monitor each for success

The setup wizard runs 9 automated steps. Each shows a green checkmark on success or a red X on failure. Monitor the progress and note any failures for troubleshooting.

  • 1. Check Prerequisites — verifies Docker, MySQL client, RabbitMQ tools
  • 2. Create MySQL Databases — creates the required application databases
  • 3. Configure RabbitMQ — creates the message broker vhost and credentials
  • 4. Generate Docker Compose — writes docker-compose.yml with all 11 containers
  • 5. Pull Docker Images — downloads service images from the private registry (~2–5 GB total)
  • 6. Start Services — runs docker compose up -d
  • 7. Health Check — verifies containers are running (waits ~10 seconds)
  • 8. Configure Backups — enables automated cloud backup
  • 9. Install Daemon Service — registers puru-nucleus as a system service (systemd / launchd / Windows Service)
⚠ Step 5 (Pull Images) takes the longest. If internet is slow, consider pre-pulling images from USB using docker load -i <image>.tar

Verify Installation ~5 min

Confirm all services are running and cloud-connected

Run these verification checks to confirm everything is working end-to-end before handing over to hospital staff.

  • Check all 11 containers are running 
docker ps --format "table {{.Names}}\t{{.Status}}"
  • Access the frontend — open http://<server-ip> in a browser, should show the Puru login page
  • Check puru-nucleus dashboard at http://localhost:9090 — all services should show green
  • Verify cloud connectivity — within 15 minutes, hospital should appear as "Online" in Puru Control Center Nucleus tab
💡 Take a screenshot of the dashboard showing all green services. Send it to the admin team as confirmation of successful deployment.

7

Handover ~5 min

Brief hospital staff and finalize deployment

Walk the hospital IT staff through the basics. They don't need to manage services day-to-day (the daemon and cloud admin handle that), but they should know what's running and who to contact.

  • Show hospital IT staff the puru-nucleus dashboard at http://localhost:9090
  • Explain: backups run automatically every 24 hours
  • Explain: the admin team can send commands remotely (restart services, trigger backups)
  • Explain: if a service goes down, watchdog alerts are sent to the cloud automatically
  • Note the API key from the nucleus config — needed if hospital IT needs direct API access
🔒 Never share the credentials file. It provides direct access to the hospital's cloud resources, backups, and data.
Section 2

Existing Hospital Maintenance

Troubleshooting, maintenance visits, and adopting pre-existing installations into the puru-nucleus management framework.

⏱ Variable — depends on issue complexity
☑

Pre-Visit Checklist

Review hospital status before departing

Before traveling to the hospital, review its current state in the cloud dashboard. Understanding the situation upfront saves time on-site.

  • Check hospital status in Puru Control Center Nucleus tab — note any alerts or offline services
  • Check recent commands history — see if any commands failed
  • Check messaging inbox — any unread messages from the hospital?
  • Bring: laptop, USB with latest puru-nucleus binary, latest Docker image tarballs (if updating offline)
1

Assess Current State ~5 min

SSH in and check system health

Get a quick health snapshot of the server. Run these commands in order to understand what's working and what isn't.

  • SSH into hospital server
  • Check puru-nucleus daemon status 
# Linux
systemctl status puru-nucleus

# Windows — check Services panel or:
sc query PuruNucleus
  • Check running containers 
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
  • Check disk usage (warn if >85%) 
df -h /
  • Check memory (warn if available <1 GB) 
free -h
  • Check recent nucleus logs 
journalctl -u puru-nucleus --since "1 hour ago" --no-pager | tail -50
2

Common Issues & Fixes

Troubleshooting playbook for the most frequent problems

Service Won't Start

  • Check the service's logs for the error 
docker logs <container-name> --tail 50
ℹ Common cause: MySQL not ready. Restart MySQL first, wait 30 seconds, then restart the failed service. 
docker restart purusql
sleep 30
docker compose -f <compose-path> restart <service-name>
ℹ Common cause: Port conflict. Find the conflicting process: 
ss -tlnp | grep <port>

Nucleus Offline in Cloud

  • Check internet connectivity 
curl -s https://cloud.google.com -o /dev/null -w "%{http_code}"
  • Verify credentials file exists 
# Check credentials file exists at the configured path
ls -la /etc/puru-nucleus/gcs-credentials.json
  • Check and restart daemon 
systemctl is-active puru-nucleus
systemctl restart puru-nucleus

Backup Failures

  • Check backup-specific logs 
journalctl -u puru-nucleus --grep "backup" --since "24 hours ago"
  • Verify credentials are still active in the Control Center Credentials tab
  • Trigger a manual backup to test 
# Via cloud: Control Center → Nucleus tab → "Trigger Backup"
# Or locally via API:
curl -H "X-API-Key: <api-key>" http://localhost:9090/api/backup

Need to Update Services

  • Online: Admin sends update command from Puru Control Center Nucleus tab
  • Manual pull: 
docker compose -f <compose-path> up -d
  • Offline update (from USB tarball): 
docker load -i puru-xenon-latest.tar
docker compose -f <compose-path> up -d

Credential Issues (Regenerate/Revoke)

  • If credentials are compromised: Admin revokes from the Control Center Credentials tab, then generates new ones
  • Receive the new credentials file and replace the existing one on-site 
sudo cp <new-credentials-file> /etc/puru-nucleus/gcs-credentials.json
sudo systemctl restart puru-nucleus
3

Adopt Existing Installation ~10 min

Add nucleus daemon to a hospital with existing Puru containers

If the hospital already has running Puru containers but no puru-nucleus daemon, you can adopt the existing setup instead of reinstalling from scratch. The wizard detects existing containers and extracts their configuration.

  • Install puru-nucleus binary (same as New Setup → Step 2)
  • Run the setup wizard 
puru-nucleus setup
  • Wizard detects existing containers — choose "Adopt Existing"
  • Wizard extracts credentials from existing .env files, skips database and RabbitMQ setup
  • Daemon service is registered and starts monitoring
  • Activate with cloud credentials (same as New Setup → Step 3)
ℹ The "Adopt Existing" path is significantly faster because it skips database creation, RabbitMQ configuration, and Docker image pulling. It only registers the daemon and connects to the cloud.
4

Post-Visit Checklist ~5 min

Confirm everything is healthy before leaving

Before leaving the hospital, run through these final checks to make sure everything is stable and cloud-connected.

  • Verify all services running: docker ps shows all containers
  • Verify nucleus is online: Puru Control Center Nucleus tab shows "Online" with green dot
  • Clear any acknowledged alerts in the Nucleus tab
  • Send a test message from Puru Control Center Messaging tab to verify inbox connectivity
  • Document any issues found and fixes applied — add notes to the hospital record
